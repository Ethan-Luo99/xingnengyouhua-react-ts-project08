# 函数执行监控面板 — 增量重算落地说明

基于 `PERF-ANALYSIS.md` 的方案 A（依赖图 + 增量重算）+ 方案 D（汇总区精准订阅）实现。
零新增 runtime 依赖；测试使用 Node 内置 `node:test`（仓库原本没有测试框架，
按约束未引入 vitest——如需迁移，测试文件结构可直接复用）。

## 结构

| 文件 | 职责 |
|---|---|
| `registry.ts` | 600 个业务函数注册表（Map 插入序 = 执行序）：20 解析器 + 540 叶子（3 层真实依赖链）+ 40 汇总；每个函数 busy-wait 约 0.4ms，全量 > 200ms |
| `engine.ts` | 增量重算核心：DAG、dirty 传播、版本号、Proxy 兜底、动态增删、环检测 |
| `store.ts` | 框架无关的状态 store：汇总快照浅比较缓存（精准订阅的关键） |
| `index.ts` | 单例装配 + HMR 钩子（registry 热替换 → 整体失效） |
| `react.ts` / `SummaryPanel.tsx` | `useSyncExternalStore` 绑定；汇总区独立 memo 组件 |
| `busyWait.ts` | 同步空转注入，模拟单函数 0.4ms 耗时 |

## 关键设计取舍

### 执行模型：单趟顺序扫描 = 拓扑序

注册表构造时保证所有依赖边从**先注册者**指向**后注册者**，因此 Map 插入序
本身就是合法拓扑序。增量执行只是一次"带跳过的全量顺序扫描"：函数被跳过
当且仅当它的所有读字段值都未变（`Object.is` 值级裁剪），其输出必然不变，
故顺序敏感语义与全量执行**严格等价**（等价性由快照 diff 为空的单测保证）。

### 第 4 条决策：显式声明为主，Proxy 读追踪兜底

**选择：两者结合，而不是二选一。**

- **显式声明（reads/writes）是真相之源**：静态、零开销、可审计，是 DAG 的
  构建依据。纯 Proxy 方案无法替代它——Proxy 只能看到"已经执行过"的函数
  实际读了什么，首轮执行前没有依赖信息；且读追踪无法区分"读 input.text"
  与"读 window 状态"这类系统外依赖。
- **Proxy 是运行时兜底**：执行期用 Proxy 包装 ctx，记录每个函数的实际读写字段；
  发现未声明的隐式依赖时**自动补动态边**（后续轮次 dirty 传播即精确），
  并通过 `onImplicitDep` 回调上报（开发期可接告警）。没有这层兜底，漏声明
  就是静默脏缓存（见单测"Proxy 读追踪兜底隐式依赖"）。
- **降级策略**（两条）：
  1. 隐式依赖的写入者排在该函数**之后**（拓扑序无法与插入序等价）→ 该函数
     降级为 `alwaysDirty`，每轮必执行——用性能换正确性，绝不返回脏结果；
  2. `trackReadsWithProxy: false` 可整体关闭追踪（如极端性能敏感的生产路径），
     退化为纯显式声明，代价是漏声明不再被检测。

### 版本号与批次隔离

每轮执行的所有写入先进 **overlay**（函数读取时 overlay 优先），仅在提交点
校验版本号后才合并进共享 ctx。输入连续触发时，旧版本批次在下一个切片边界
检测到版本过期即中止，overlay 整体丢弃——旧批次结果物理上不可能覆盖新结果。
分片执行（`applyInputChunked`，默认 24ms 预算）用于首帧全量计算，避免
240ms 长任务；按键增量（< 100 函数、< 50ms）走同步路径。

### 兼容性硬约束的对应实现

- **StrictMode**：重算只在事件回调 / effect 中触发，render 只读快照；
  `ensureComputed()` 幂等（in-flight 复用 + 失效标志位），双调用不重复执行。
- **HMR**：`index.ts` 中 `import.meta.hot.accept('./registry.ts', …)` →
  `replaceRegistry`：缓存与 DAG 整体失效、版本号 +1（在飞批次过期）、
  下一轮全量重算。
- **动态增删**：`registerFunction` / `unregisterFunction` 增量维护索引；
  注册时先做环检测（成环抛 `CycleError`）再校验拓扑序与插入序等价
  （违反抛 `OrderError`），任一失败整体回滚；注销时将其写字段标记为
  已变化，下游下一轮按全量语义重算。
- **汇总区精准订阅**：`store.getAggSnapshot()` 对 40 个 agg 输出做浅比较，
  未变则返回同一引用；`useSyncExternalStore` + `memo` 保证未变化的输入
  不触发 `SummaryPanel` render（render 计数在页面上实时可见）。

## 验证方法

```bash

                # 环检测、HMR 失效、StrictMode、版本丢弃、Proxy 兜底
npm run bench   # 基准：模拟连续按键，输出优化前后对比报告并断言
                # 重算函数数 < 100、单次阻塞 < 50ms
npm run dev     # 手动验证：输入框打字，观察"重算/跳过"计数与汇总区 render 次数
npm run build   # 类型检查 + 生产构建
```

基准实测（本机）：基线每次按键 600 函数 / 约 243ms；优化后平均 35 函数 /
14ms，峰值 84 函数 / 34ms。

## 已知边界

- 函数若依赖 ctx 之外的可变状态（时间、随机数、模块级变量），任何基于
  输入的缓存都会脏——这是场景本身的约束，需业务侧保证函数是 ctx 的纯函数。
- 运行时注册的新函数只能追加在插入序末尾，且不得写出已被读取的字段
  （否则抛 `OrderError`）——这是"拓扑序 ≡ 插入序"等价性保证的代价。

## Undo：字段级历史 + 增量恢复

### 历史记录结构（无全量快照）

每次**成功提交**生成一条 `BatchLog` 压入 undo 栈（默认保留 50 层）：

```
BatchLog {
  changes:     Map<字段名, 提交前旧值>   // 只含本批 overlay 中 !Object.is(旧,新) 的字段
  firstForced: Set<函数名>              // 本批首次执行的动态注册函数
  fromFull:    boolean                  // 是否为冷启动整体失效点上的批次
}
```

- **空间复杂度 O(单批次实际改变的字段数 + 首执行动态函数数)**，与 ctx 总大小无关，
  不做任何 ctx 深拷贝；写了但值未变的字段不记录，`ABSENT` 哨兵区分"旧值为
  undefined"与"键原本不存在"（恢复时后者执行 `delete`）。
- **恢复走增量路径**：`undoLastBatch()` 弹出栈顶日志，把旧值放进一个新的 overlay
  （ctx 仍不动），仅将这些字段标记为 changed，然后跑同一趟顺序扫描 + dirty 传播——
  只有"读这些字段"的下游函数重算（按键场景实测 20~30 个，非 600 全量）。恢复成功
  后 overlay 落盘为新的提交点，但**不产生新的日志**（撤销被消费，不是 redo）。
- `firstForced`：动态注册函数的首执行只由结构变更触发、与输入无关，undo 重放时
  必须同样强制它执行一次，否则其输出字段不在任何 changed 集合中会被错误跳过；
  结构本身（注册/注销）不随 undo 撤销。
- `fromFull`：撤销冷启动首批时不存在可增量命中的"上一派生态"（此前派生字段
  不存在），该次恢复整体重算一次；真实面板首帧 `ensureComputed()` 已建立基线，
  用户按键批次永不命中此分支。
- 等价性：任意 `a → b → undo → c`，恢复后 ctx（含下游联动字段）与只经历 `a → c`
  的全量结果逐字段一致，由同一套"值级裁剪 + 顺序扫描"机制保证。
- 汇总区快照：`PanelStore` 另维护一个与引擎 undo 栈等长的快照**引用**栈，undo 时
  直接还原为该提交点的同一数组引用，保证精准订阅行为历史一致。

### undo 期间到达的新输入：版本丢弃（不排队、不合并）

取舍：undo 与普通批次共用版本号通道。undo 分片执行期间到达的新输入会
`version+1`，undo 在下一切片边界检测过期即中止、overlay 丢弃，其撤销点在
`beginUndo` 出栈时即视为**已消费**——与引擎既有"旧批次整体丢弃、绝不覆盖新结果"
语义完全一致；新输入照常成功提交，栈深度变化为 −1（消费）+1（新提交）。
理由：

1. **语义最可预测**：用户在撤销过程中继续输入，最新意图就是新输入本身；排队重做
   undo 会把已经被用户新动作否定的历史再倒回去，产生反直觉的状态跳变。
2. **复用已有机制零特例**：不需要 undo 专用锁或队列，也不会出现"undo 半应用 +
   新输入"的混合 overlay；StrictMode 双调用、HMR 失效、版本丢弃路径对 undo 同样成立。
3. 同步路径下（按键场景默认）undo 在一个事件回调内完成，物理上不存在"undo 期间
   插入输入"；该取舍只影响显式使用 `undoLastBatchChunked` 的长批次。

### 批次原子性与错误上报

输入补丁也只暂存进 overlay（不再先写 ctx）。任一业务函数抛错时立即中止扫描、
overlay 整体丢弃，ctx 保持在上一提交点，引擎不进入半提交状态；错误经
`EngineOptions.onBatchFailure({ version, fnName, error })` 明确通道上报，
`RunStats.failed` 为 true，失败批次不发订阅通知、不入 undo 栈。启动时抽干的
待处理动态函数/字段会在失败后归还，因此连续失败后第 4 次成功仍与从未失败的
全量结果一致。HMR 替换注册表时 undo 历史一并作废（字段旧值对新实现无语义意义）。
